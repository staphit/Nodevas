# 輸入方式：滑鼠鍵盤與觸控

同一份前端同時是桌面網頁、行動裝置網頁，以及 iOS App 內的畫面。這份文件說明它怎麼分辨使用者當下用什麼在操作，以及為什麼是這樣分。

## 原則：以事件判別，不以裝置判別

判斷寫在每一個 pointer 事件上，不是在啟動時決定一次。

```ts
if (event.pointerType !== "mouse") { /* 觸控／觸控筆 */ }
```

理由：一台裝置可以同時有兩種輸入。iPad 接上巧控鍵盤、觸控筆與手指交替、觸控螢幕筆電——啟動時決定一次，就一定會有一半的操作被判錯。滑鼠路徑因此完全沒有改動，觸控只是多一條路進來。

實作在 `src/components/touch.ts`。

## 對應表

| 操作 | 滑鼠鍵盤 | 觸控 |
|---|---|---|
| 開啟情境選單 | 右鍵 | 長按 500ms（位移 >10px 視為拖曳，不觸發） |
| 畫布縮放 | `Alt` ＋滾輪 | 雙指捏合 |
| 畫布平移 | 拖曳空白處 | 單指拖曳空白處 |
| 建立關係線 | `Alt` ＋從節點拖曳 | 切到「連線」手勢後，從節點拖曳 |
| 新增線條轉折點 | `Alt` ＋點擊關係線 | 切到「連線」手勢後，點擊關係線 |
| 框選多個節點 | `Ctrl`／`⌘` ＋拖曳 | 切到「框選」手勢後拖曳 |

前三項有直接對應的觸控慣用手勢，直接對應。後三項沒有——手指按不出 `Alt`——所以改成畫布工具列上一個看得見的三段切換（選取／連線／框選），定義在 `src/components/canvas/gestureMode.ts`。修飾鍵在任何模式下都仍然有效，模式只是多一條路，不是取代。

## 長按怎麼實作

在 root 掛一次監聽，長按時對被按住的元素 `dispatchEvent` 一個真正的 `contextmenu` 事件。

全 app 的選單本來就都是 `onContextMenu`——卡片、關係線、邏輯閘、專案樹、時間軸儲存格、分頁——所以一律零改動生效，包含那些用 `stopPropagation` 從父層搶走事件的。若改成把 hook 逐一接到每個呼叫點，每個都得自己重做一次那套派發，而且下次有人新增選單時一定會忘記接。

文字輸入區（`input`、`textarea`、CodeMirror）排除在外：那裡的長按屬於系統的選字與放大鏡，搶走它等於讓手機沒辦法選字。

## 什麼時候顯示觸控專屬的 UI

- **顯示與否**用 `useTouchCapable()`（`any-pointer: coarse`）：只要裝置「有」觸控螢幕就給。iPad 接鍵盤後主要指標會變成 fine，但手指還是會碰畫布，此時把手勢切換藏起來等於把那些手勢整個拿掉。
- **尺寸與間距**用 CSS `@media (pointer: coarse)`：主要指標是手指時才放大點擊區（44px），滑鼠使用者不需要為觸控付出版面。
- **版面**用寬度斷點 `@media (max-width: 720px)`，跟指標種類無關——把視窗拉窄的桌面瀏覽器，需要的是同一套窄版版面。

三個問題不同，所以用三種判斷，不要混為一談。

## 頁面縮放

`index.html` 沒有停用 `user-scalable`。把網頁的縮放拿掉，等於把它從所有需要放大才看得清楚的人手上拿走。畫布自己的捏合縮放不會跟它打架：畫布是 `touch-action: none`，瀏覽器根本收不到那個手勢；iOS App 那層則是在 Swift 直接關掉 web view 的捏合。
